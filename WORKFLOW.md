# FE-03 Workflow Comparison

For this assignment, I built the same small feature twice in a fresh repo: a career alert preferences form for a TalentDash-style product. The branches are `fe-03-vague-settings-form` and `fe-03-precise-settings-form`.

The vague round was intentionally loose. I treated it like a one-line prompt: build an alert settings form. The result was quick and looked acceptable at first glance, but it only used local `useState`, free-text inputs, a frequency dropdown, and a generic success message. The actual diff was small: 121 insertions across `src/App.tsx` and `src/index.css`. That speed was nice, but the correctness burden shifted to manual review. The form accepted any email shape, allowed inconsistent location input, had no constrained alert types, no formal validation rules, and no automated tests. It ran, but it did not prove much.

The precise round was built with clearer constraints: keep the feature small, use reusable validation, constrain options, surface errors in the UI, and verify with tests plus a build. That branch is much larger, with 943 insertions across six files. The increase was not just extra UI polish. It added `src/lib/alertPreferences.ts` for defaults, allowed values, schema validation, and summary formatting, plus `src/lib/alertPreferences.test.ts` for automated verification. The app also gained structured checkbox groups, accessible field errors, a preview card, and a real `npm test` script in `package.json`.

Correctness improved the most in round two. Email format, required selections, and compensation bounds are all enforced before save. Accessibility improved because the stronger version has explicit field grouping, invalid states, and inline error text rather than only visual layout. Edge cases are clearer too: empty multi-select groups, malformed email input, and compensation outside the allowed range now fail predictably instead of slipping through.

The biggest lesson was that the precise round felt slower at the start but faster by the end. The vague branch was quicker to generate, but I would have had to do much more human cleanup before trusting it. In the stronger branch, the verification loop caught two AI mistakes: I initially wrote a broken test fixture, and I also missed an explicit React import needed for the TypeScript build. Those catches are exactly why the tighter prompt plus verification workflow is better. The extra upfront specificity reduced review guesswork and made the final result easier to trust.
